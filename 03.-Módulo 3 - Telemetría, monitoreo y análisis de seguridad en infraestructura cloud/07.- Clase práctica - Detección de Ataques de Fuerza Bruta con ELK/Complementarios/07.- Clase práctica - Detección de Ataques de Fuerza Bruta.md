# Clase práctica: Detección de ataques de fuerza bruta con ELK

## Propósito de la sesión

Esta sesión no introduce una práctica completamente nueva. Su propósito es continuar, completar y depurar la actividad de detección de ataques de fuerza bruta con ELK iniciada en la sesión anterior.

Durante la clase, cada estudiante debe terminar de conectar los componentes del pipeline:

1. VM en Google Cloud Platform.
2. Reglas de firewall para acceder a Elasticsearch y Kibana.
3. Stack ELK ejecutándose con Docker Compose.
4. Índice de Elasticsearch para almacenar logs.
5. Agente Python para recolectar logs de `/var/log`.
6. Consultas REST para validar datos.
7. Kibana Discover para explorar eventos.
8. Dashboard para visualizar intentos fallidos, usuarios e IPs origen.

La meta es que el estudiante pueda explicar cómo un conjunto de logs crudos se transforma en evidencia útil para detectar actividad sospechosa.

## Relación con la sesión anterior

En la sesión anterior se trabajó la actividad de detección de fuerza bruta con ELK. Esa actividad incluía:

- abrir puertos en GCP;
- levantar Elasticsearch y Kibana;
- crear el índice `gcp-vm-logs`;
- definir mappings;
- ejecutar un script de ingesta en Python;
- consultar datos con la API REST;
- crear un Data View en Kibana;
- analizar eventos de autenticación fallida;
- construir visualizaciones.

Esta clase práctica está destinada a terminar lo que no haya quedado funcionando, corregir errores y construir el reporte final con evidencias verificables.

## Resultado esperado

Al finalizar la sesión, cada estudiante deberá tener:

1. Elasticsearch respondiendo por API REST.
2. Kibana accesible desde navegador.
3. El índice `gcp-vm-logs` creado.
4. Logs enviados desde la VM hacia Elasticsearch.
5. Eventos visibles en Kibana Discover.
6. Al menos una consulta KQL para detectar fallos de autenticación.
7. Al menos dos visualizaciones en Kibana.
8. Un dashboard básico de análisis.
9. Evidencias suficientes para el reporte.
10. Una reflexión técnica sobre riesgos, costos y límites de la solución.

## Regla ética y de seguridad

Esta práctica es defensiva y educativa. Solo se permite analizar logs de la infraestructura propia del estudiante o de recursos autorizados por el profesor.

No se debe intentar generar tráfico, escaneo, autenticaciones fallidas ni pruebas de fuerza bruta contra sistemas de terceros. Si se requiere generar eventos de autenticación fallida para tener datos de prueba, deben generarse únicamente contra la VM propia del estudiante y de forma controlada.

## Puertos utilizados

| Puerto | Servicio | Uso |
|---|---|---|
| 22 | SSH | Administración remota de la VM |
| 9200 | Elasticsearch | API REST e ingesta de documentos |
| 5601 | Kibana | Interfaz web de análisis |

Los puertos `9200` y `5601` deben abrirse solo para la práctica y preferentemente restringirse a la IP pública del estudiante cuando sea posible.

## Organización de la clase

### 1. Diagnóstico inicial del avance

Cada estudiante debe comenzar identificando en qué punto se encuentra:

- no tengo VM;
- tengo VM, pero no tengo Docker;
- Docker está instalado, pero ELK no levanta;
- Elasticsearch levanta, pero Kibana no responde;
- Kibana responde, pero no hay datos;
- hay datos, pero no se clasifican eventos de autenticación;
- hay datos y necesito construir visualizaciones;
- ya tengo dashboard y necesito documentar.

El profesor revisará avances a partir de esta lista y priorizará bloqueos.

### 2. Verificación de la VM

Entrar por SSH a la VM y ejecutar:

```bash
hostname
whoami
cat /etc/os-release
free -h
df -h
ip addr
```

Estas salidas ayudan a confirmar sistema operativo, usuario, memoria, disco y red.

### 3. Verificación de firewall en GCP

Revisar que existan reglas de entrada para los puertos `9200` y `5601`, y que apliquen a la VM correcta.

Si se usa etiqueta de red, confirmar que la VM tenga la etiqueta esperada:

```bash
gcloud compute instances describe NOMBRE_VM --zone ZONA_VM
```

Buscar la sección `tags`.

Ejemplo de reglas de firewall:

```bash
gcloud compute firewall-rules create allow-kibana-ingress \
  --allow=tcp:5601 \
  --direction=INGRESS \
  --priority=1000 \
  --network=default \
  --target-tags=elk-server

gcloud compute firewall-rules create allow-elasticsearch-rest \
  --allow=tcp:9200 \
  --direction=INGRESS \
  --priority=1000 \
  --network=default \
  --target-tags=elk-server
```

Asignar la etiqueta a la VM:

```bash
gcloud compute instances add-tags NOMBRE_VM \
  --tags=elk-server \
  --zone=ZONA_VM
```

Si la regla ya existe, no se debe duplicar. En ese caso se revisa la regla existente.

### 4. Verificación de Docker y ELK

Dentro de la VM:

```bash
docker --version
docker compose version
docker ps
```

Si el repositorio `docker-elk` ya existe:

```bash
cd ~/docker-elk
docker compose ps
docker compose logs --tail=80 elasticsearch
docker compose logs --tail=80 kibana
```

Si el stack no está arriba:

```bash
cd ~/docker-elk
docker compose up -d
```

Validar puertos:

```bash
ss -tulpn | grep -E "9200|5601"
```

Resultado esperado:

- Elasticsearch escuchando en `9200`.
- Kibana escuchando en `5601`.
- Contenedores en estado `Up`.

### 5. Validación de Elasticsearch

Desde la VM:

```bash
curl http://localhost:9200/_cluster/health?pretty
```

Desde la computadora local, usando la IP pública:

```bash
curl http://IP_PUBLICA_VM:9200/_cluster/health?pretty
```

El estado `yellow` es aceptable en un laboratorio de un solo nodo. Significa que los shards primarios funcionan, aunque no hay réplicas en otro nodo.

### 6. Validación de Kibana

Abrir en el navegador:

```text
http://IP_PUBLICA_VM:5601
```

Si no abre:

- revisar firewall de GCP;
- revisar si el contenedor de Kibana está arriba;
- revisar logs de Kibana;
- confirmar que la URL usa `http://`;
- confirmar que la IP pública corresponde a la VM correcta.

## Creación o revisión del índice

El índice esperado es:

```text
gcp-vm-logs
```

Desde Kibana Dev Tools o usando `curl`, revisar:

```bash
curl http://localhost:9200/gcp-vm-logs?pretty
```

Si el índice no existe, crearlo con un mapping explícito:

```bash
curl -X PUT "http://localhost:9200/gcp-vm-logs" \
  -H "Content-Type: application/json" \
  -d '{
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },
        "log_file": { "type": "keyword" },
        "hostname": { "type": "keyword" },
        "host": { "type": "keyword" },
        "collector_host": { "type": "keyword" },
        "process": { "type": "keyword" },
        "event_type": { "type": "keyword" },
        "username": { "type": "keyword" },
        "source_ip": { "type": "ip" },
        "message": { "type": "text" },
        "raw_line": { "type": "text" },
        "raw_timestamp": { "type": "keyword" }
      }
    }
  }'
```

Si el índice ya existe con un mapping incorrecto, se debe documentar el problema antes de borrar. Para reiniciar el índice:

```bash
curl -X DELETE "http://localhost:9200/gcp-vm-logs"
```

Luego se vuelve a crear el índice con el mapping correcto.

## Agente Python de ingesta

La carpeta de la actividad anterior contiene dos archivos de apoyo:

- `setup_env.sh`
- `collect_varlog_to_elk.py`

El objetivo del agente es leer archivos de `/var/log`, transformar líneas de log en documentos JSON y enviarlos a Elasticsearch.

### Preparar entorno Python

En la VM:

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip file
```

Crear entorno:

```bash
python3 -m venv elk-logs-env
source elk-logs-env/bin/activate
pip install requests
```

Si se usa `setup_env.sh`:

```bash
chmod +x setup_env.sh
./setup_env.sh
source elk-logs-env/bin/activate
```

### Revisar el script antes de ejecutarlo

Antes de correr el agente, cada estudiante debe revisar:

- URL de Elasticsearch;
- usuario y contraseña si el stack tiene autenticación;
- índice de destino;
- límite de líneas por archivo;
- exclusión de archivos binarios;
- permisos de lectura sobre `/var/log`.

Ejemplo de endpoint si el script corre dentro de la misma VM:

```python
ELASTIC_URL = "http://localhost:9200/gcp-vm-logs/_doc"
```

Ejemplo de endpoint si el script corre desde otra máquina:

```python
ELASTIC_URL = "http://IP_PUBLICA_VM:9200/gcp-vm-logs/_doc"
```

No se deben publicar contraseñas ni tokens en el reporte.

### Ejecutar el agente

```bash
source elk-logs-env/bin/activate
python3 collect_varlog_to_elk.py
```

Si aparecen errores de permisos en `/var/log`, se puede ejecutar con `sudo`, pero documentando la razón:

```bash
sudo elk-logs-env/bin/python collect_varlog_to_elk.py
```

Resultado esperado:

- lista de archivos detectados;
- mensajes de procesamiento;
- conteo final de documentos enviados;
- documentos visibles en Elasticsearch.

## Generación controlada de eventos de autenticación fallida

Si la VM no tiene suficientes eventos de autenticación fallida, se pueden generar intentos fallidos de forma controlada contra la VM propia.

Desde la computadora del estudiante:

```bash
ssh usuario_inexistente@IP_PUBLICA_VM
```

Ingresar una contraseña incorrecta y cancelar después de pocos intentos.

Reglas:

- hacerlo solo contra la VM propia;
- no automatizar diccionarios;
- no ejecutar ataques contra terceros;
- no saturar la VM;
- documentar que se generaron eventos controlados de prueba.

Después, volver a ejecutar el agente de ingesta para enviar los nuevos logs a Elasticsearch.

## Consultas REST de validación

### Conteo total de documentos

```bash
curl "http://localhost:9200/gcp-vm-logs/_count?pretty"
```

### Buscar eventos relacionados con autenticación fallida

Si el script clasifica `event_type`:

```bash
curl -X GET "http://localhost:9200/gcp-vm-logs/_search?pretty" \
  -H "Content-Type: application/json" \
  -d '{
    "query": {
      "term": {
        "event_type": "authentication_failure"
      }
    }
  }'
```

Si todavía no existe `event_type`, buscar en el mensaje:

```bash
curl -X GET "http://localhost:9200/gcp-vm-logs/_search?pretty" \
  -H "Content-Type: application/json" \
  -d '{
    "query": {
      "match": {
        "message": "Failed password"
      }
    }
  }'
```

### Top de IPs origen

```bash
curl -X GET "http://localhost:9200/gcp-vm-logs/_search?pretty" \
  -H "Content-Type: application/json" \
  -d '{
    "size": 0,
    "aggs": {
      "top_source_ip": {
        "terms": {
          "field": "source_ip",
          "size": 10
        }
      }
    }
  }'
```

### Top de usuarios

```bash
curl -X GET "http://localhost:9200/gcp-vm-logs/_search?pretty" \
  -H "Content-Type: application/json" \
  -d '{
    "size": 0,
    "aggs": {
      "top_usernames": {
        "terms": {
          "field": "username",
          "size": 10
        }
      }
    }
  }'
```

## Guía de troubleshooting

### Elasticsearch no responde

Revisar:

```bash
docker ps
docker compose logs --tail=80 elasticsearch
curl http://localhost:9200/_cluster/health?pretty
free -h
```

Posibles causas:

- contenedor caído;
- falta de memoria;
- puerto no expuesto;
- Docker no está ejecutando;
- Elasticsearch aún está iniciando.

### Kibana no abre

Revisar:

```bash
docker ps
docker compose logs --tail=80 kibana
ss -tulpn | grep 5601
```

Posibles causas:

- Kibana aún está arrancando;
- firewall no permite `5601`;
- IP pública incorrecta;
- contenedor caído;
- Elasticsearch no está listo.

### El agente Python no envía documentos

Revisar:

```bash
python3 --version
source elk-logs-env/bin/activate
python3 -c "import requests; print('requests ok')"
curl http://localhost:9200/gcp-vm-logs/_count?pretty
```

Posibles causas:

- endpoint incorrecto;
- autenticación incorrecta;
- falta `requests`;
- permisos insuficientes para leer `/var/log`;
- índice no existe;
- mapping incompatible.

### No aparecen eventos de fuerza bruta

Revisar:

- si existen líneas de autenticación fallida en `/var/log/auth.log`;
- si el sistema usa otro archivo de logs;
- si el parser reconoce los patrones;
- si `event_type` se está generando correctamente;
- si Kibana está filtrando un rango temporal incorrecto.

Buscar en la VM:

```bash
sudo grep -Ei "failed password|invalid user|authentication failure" /var/log/auth.log
```

Si no existe `/var/log/auth.log`, revisar:

```bash
ls -lah /var/log
journalctl -u ssh --no-pager | tail -50
```

### Error de mapping

Si Elasticsearch rechaza documentos con `document_parsing_exception`, revisar:

- tipo del campo `source_ip`;
- campos enviados por Python;
- mapping del índice;
- documentos previos que hayan creado mapping dinámico incorrecto.

Ver mapping:

```bash
curl http://localhost:9200/gcp-vm-logs/_mapping?pretty
```
